# Project Git commit timeout / index.lock reconnaissance

Read-only analysis on 2026-11-02. Baseline HEAD: `a38080dae4a36772037d786856087bc370725f0a`. “WT” means the existing working-tree candidate, not a proposed patch. References use `HEAD:path:line` or `WT:path:line`; a reference without a revision in a WT discussion means WT. Only this report was written; no build, tests, formatting, or Git mutations were run. Existing unrelated changes were preserved.

## Verdict and root-cause chains

The candidate reduces the likelihood of the reported failure but does **not** fully fix it. It raises subprocess/client budgets, explicitly kills and waits on inner timeout, serializes four mutation entry points, and attempts stale-lock recovery. It still permits request cancellation to kill an index writer without cleanup, can skip a newly written orphan lock, and can delete an external writer's live lock. Its advertised end-to-end timeout guarantee is also incorrect.

**Timeout:** expensive staging/index rewrite and commit hooks -> sequential Git subprocesses with independent server budgets -> the browser's much smaller overall request timer expires first -> AbortController aborts fetch and the UI displays `Request timed out after 12000ms`. At HEAD, the selected-path command portion alone permits add(30s) + commit(30s) + final log(5s) = **65s**, plus ensure_repo(5s) = **70s**, against a **12s** default client deadline. With no selected paths, commit + log + ensure permits **40s**. A timeout does not establish that no commit was created.

Evidence: `HEAD:ui/hub-core/src/rest.ts:105,160-181,216-224,232-238`; `HEAD:crates/openduck/src/control/git.rs:12-16,279-289,747-790`. WT moves the core phases to 60 + 120 + 30 = 210s and client commit fallback to 240s (`WT:crates/openduck/src/control/git.rs:165-172,1015-1069`; `WT:ui/hub-core/src/rest.ts:105-112,193-242`), but excludes additional work and mutex wait from that 210s claim. See full arithmetic below.

Large repositories and slow filesystems increase traversal, file hashing/filter execution, and index serialization costs during add/commit. The selected-path flow runs `git add -- paths` followed by `git commit --no-status -F file -- paths`; Git's path-limited commit can prepare/write index state again. `--no-status` suppresses status text in the commit message; it neither skips staging/index work nor disables hooks. Pre-commit, prepare-commit-msg, commit-msg, post-commit hooks, signing, and hook subprocesses consume the same commit budget. `git_command` disables fsmonitor but not commit hooks (`WT:crates/openduck/src/subprocess.rs:34-44`). These are mechanisms explaining susceptibility, not measured timings for this user's repository.

**Lock residue:** Git creates `index.lock` as an exclusive lock and temporary index -> timeout/drop kills Git while that lock exists -> SIGKILL cannot execute Git's normal rollback/unlink/rename cleanup -> lock file remains -> later index writers fail to acquire it. At HEAD, `tokio::time::timeout(..., command.output())` owns the output future; expiry drops it, dropping its Child with `kill_on_drop(true)` (`HEAD:crates/openduck/src/control/git.rs:176-204`). This is forceful termination on Unix, not graceful Git shutdown. There is no post-failure lock cleanup or pre-mutation stale-lock recovery anywhere in HEAD's runner or stage/unstage/discard/commit (`HEAD:crates/openduck/src/control/git.rs:192-223,661-790`). The lock does not become harmless merely by getting old. Without outside cleanup, subsequent index-writing operations keep failing indefinitely. Read-only commands may still work; “all Git operations” is the user-visible symptom, not a literal property of every Git command.

**Independent cancellation route:** the browser abort/disconnect may cause Hyper to drop the request's service/handler future -> HTTP handler directly awaits `git::commit` -> entire nested Git future is dropped -> Child's kill-on-drop kills the writer without reaching ordinary async cleanup. This can happen before the server's own timeout, or while cleanup is running. `git_commit` is identical at `HEAD` and `WT:crates/openduck/src/control/http.rs:1345-1353`; its WT diff contains unrelated formatting only. WT retains `kill_on_drop(true)` at `git.rs:340`. No Drop guard, detached operation owner, or guaranteed cleanup supervisor exists in this path (`git.rs:36-43,368-435,1015-1069`).

Disconnect qualification: fetch abort is not a universal immediate server cancellation signal; a proxy can retain the upstream request, or Git may already have finished. It **can** cancel this handler, and the code must tolerate it. The repository uses Axum serve / axum-server (`crates/openduck-cli/src/cli.rs:1573-1598`). Locally inspected locked dependencies support the mechanism: Hyper 1.10.1 HTTP/1 `src/proto/h1/dispatch.rs:49,173-174,591-624` stores the service future in the connection; `src/proto/h1/conn.rs:491-504` returns an error on mid-message EOF with half-close disabled (default at line 54). Ending/dropping the connection drops that future. HTTP/2 `src/proto/h2/server.rs:448-460` terminates a pending service stream on RST_STREAM. Tokio 1.53.1 `src/process/mod.rs:1065-1071,1123-1127,1240-1250` shows output owning Child, kill-on-drop, and Unix SIGKILL. Dependency sources were read from `/home/zhanghu/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/`; no disconnect reproduction was run.

### Commit latency arithmetic

At HEAD, selected paths: `ensure(5) + add(30) + commit(30) + final-log(5) = 70s`; already-staged/no paths: `5 + 30 + 5 = 40s`. Phase values are maxima approached by successful commands; a timed-out add stops the sequence. Twelve seconds is smaller even than a single allowed 30-second write, so sequential composition is not required to trigger the mismatch.

WT's quoted `60 + 120 + 30 = 210s` only counts the principal commands. With selected paths and no lock present, the actual sum of configured phase budgets on the successful path is:

```
ensure_repo                     30
recover: index_lock_path        30
git add                         60
add cleanup: index_lock_path    30
git commit                     120
commit cleanup: index_lock_path 30
post-commit log                 30
total                          330 seconds
```

Each cleanup calls rev-parse even when no lock exists. WT without selected paths is `30+30+120+30+30 = 240s`, leaving no client margin. Recovering an existing aged lock adds a toplevel lookup (30s) plus removal retries. If either post-command cleanup finds a lock, it also attempts a toplevel lookup (30s) and possibly removal. These conditional paths add further latency, not included in 330s. Mutex queue time is unbounded and is inside the client request timer. Killing/reaping and synchronous filesystem operations are not covered by a whole-operation deadline. Thus **there is no finite guaranteed end-to-end maximum**, and 240s cannot guarantee the client outlives the server. This is a budget analysis, not a claim that rev-parse normally needs 30s.

Other route sums also exceed WT defaults even without queueing/locks: status `30+30=60s`; history with HEAD `30+30+30+30=120s`; tracked-file diff (which calls status) `30+60+30=120s`; show `30+30+30=90s`. HEAD equivalents are 10s, 23s, 23s, and 21s. Stage WT is `ensure30+recover30+add90+cleanup30+status60=240s` against client 120s (HEAD 45s against 12s). Unstage with staged changes adds a status before restore, giving 300s WT (55s HEAD). Discard performs sequential per-path commands, sometimes restore plus clean for one path; it has no path-count-independent total budget. Message suggestion can consume `ensure30 + status60 + two-diffs60 + model90 = 240s`, plus provider creation, against client 90s (HEAD phase sum 56s against 12s). Worktree add permits `ensure30 + first-add90 + fallback-add90 = 210s` if the first command exits unsuccessfully rather than timing out; remove permits 120s. No worktree HTTP route/client method was found in this control router/rest client.

### Exact client precedence

After the earlier special-case route returns, `requestTimeoutMs` chooses:

1. Explicit `options.timeoutMs` (WT `rest.ts:234-235`), including 0 -> no timer.
2. Valid nonnegative localStorage `openduck.api.timeoutMs` (`rest.ts:137-145`).
3. Environment `VITE_API_TIMEOUT_MS`: `process.env` is checked before `import.meta.env` (`rest.ts:150-159`). A truthy process value is selected first, even if invalid; an invalid selected value falls through to the fallback rather than trying the import.meta value.
4. Git route fallback (240/90/120/30s), otherwise 12s (`rest.ts:193-200,233-242`).

So an options/config value of 12000 recreates the original early abort even for commit. Zero configuration disables it. The candidate's tests explicitly retain options override semantics (`ui/hub-core/src/rest.test.ts:725-739`). The route budget is a fallback, not a floor. Normal App construction has no options override, but persisted/environment settings still apply.

## Lock cleanup, concurrency, and bypass audit

- **Fresh orphan is a real hole, but not inevitable on every timeout.** `cleanup_orphaned_index_lock` reads mtime and returns if age <10s (`git.rs:423-433`). A killed writer can have just written/re-written the lock, so its mtime can be milliseconds old even though the process ran for 60/120s. Conversely, a writer that created an empty lock before a long hook may leave an old-enough lock and this branch can remove it. “Killed process implies fresh lock” is not universally true. The bug is that known-child failure and unknown preexisting-lock recovery share the age heuristic. Age is sampled before awaiting toplevel lookup; it is not refreshed. Skipped cleanup has no scheduled retry, and an immediate next mutation rejects the lock at `recover_stale_index_lock:138`; a later guarded mutation may recover it after 10s. This improves HEAD's permanent blockage but does not guarantee cleanup.
- **Cancellation still leaks.** Async cleanup only runs if normal code reaches `git.rs:400-408`. Dropping the future skips it; dropping the mutex guard merely releases the in-process mutex, while Child drop requests a kill. There is no async wait/reap/unlink owner that survives cancellation. Cancellation can also interrupt the cleanup's own rev-parse/removal sleep. Explicit timeout handling improved; cancellation handling did not.
- **External-process exclusion is absent.** The mutex is a process-local map keyed by the supplied canonical path (`git.rs:18-43`). A terminal Git, another server process, or another program does not acquire it. Wrapping `repo_toplevel`/`index_lock_path` lookups in that mutex only orders participating calls; rev-parse neither acquires nor holds an exclusion lock covering later deletion. The existing Git `index.lock` is the external exclusion mechanism; unlinking an active one defeats it.
- **Detection is not ownership proof.** macOS/Windows always return false (`git.rs:120-123`), so any regular index lock with old enough mtime is eligible for removal while an external Git can still be working. Linux also fails open when /proc/cwd/comm cannot be read, misses `git -C repo ...` / `--git-dir` processes whose OS cwd is elsewhere, and only accepts comm exactly `git` (`git.rs:85-118`). On WSL a Windows-side Git writer may not be visible in Linux /proc. A live process can appear after the scan; the file can be replaced between metadata/scan/removal, including during retries (`git.rs:127-145,148-159,417-435`). A false positive unrelated Git in the same directory can conversely prevent recovery forever. Ten-second mtime is not proof of abandonment on any platform.
- **Mutex identity is too narrow.** Canonicalizing `/repo` and `/repo/subdir` yields distinct keys even though both use the same index (`git.rs:25-26`). TaskAutoCommit resolves its toplevel (`git.rs:1299-1307`) while HTTP uses the configured project path (`http.rs:1274-1277,1349`); projects rooted at different subdirectories can bypass mutual exclusion. Git-dir/index identity is the relevant write resource; shared worktree administration additionally needs common-dir coordination.
- **Stage/unstage/discard:** all three now use with_repo_write_lock and recover_stale_index_lock (`git.rs:902-955`). Their inner discard_one is only called from the guarded discard flow. They share cancellation/fresh-lock/unsafe-recovery problems, rather than bypassing the wrapper.
- **TaskAutoCommit:** final actual add/commit delegates to public `commit` and **does not bypass** the new writer mutex/recovery (`git.rs:1319-1352`). Capture/finish preliminary `changes` status and diff/message preparation are outside it (`git.rs:1275-1288,1292-1307,1320,1343-1349`). A snapshot used to decide task-owned paths may also age before the actual commit. The task-harness entry points are `control/project_harness.rs:995-1006,1215-1217`.
- **Worktree add/remove:** helpers bypass both wrapper and recovery (`git.rs:1466-1509`). `writes_git_index` recognizes only the first argument and excludes `worktree` (`git.rs:349-355`), so their timeout/completion receives no lock cleanup either. Worktree add writes an index in the target worktree and shared branch/administrative state; blindly cleaning the source index would be incorrect. Current source search found only test callers of these particular helpers, not exposed HTTP worktree routes; they are a latent bypass, not demonstrated as the trigger of this commit incident.
- **Reads can write:** `git status` can opportunistically refresh/write the index. Neither status nor TaskAutoCommit changes uses `--no-optional-locks` / `GIT_OPTIONAL_LOCKS=0`; status is excluded from writes_git_index (`git.rs:333-355,709-717,1275-1286`). These unguarded background/read paths can therefore contend and can leave locks if killed during an optional refresh. diff also calls status (`git.rs:818`), as does message suggestion (`git.rs:1243`).
- **No stash/status subprocess inside commit proper:** neither HEAD `git.rs:747-790` nor WT `git.rs:1015-1069` invokes stash or status. WT commit has added rev-parse checks, not a hidden status. There is no stash string in this control Git module. Separate status exists before task auto-commit/message generation and after UI commit: `ProjectGit.tsx:316-317,203-210` reloads status/history after success, with further diff effects. Git commit's internal index refresh and user hooks remain possible; `--no-status` does not remove those.

## Remaining gaps and concrete changes (severity order)

1. **Potential active-lock deletion / data integrity risk.** `git.rs:85-145,148-159,413-435`: stop treating age + absence from a best-effort process scan as proof of orphanhood, especially the unconditional false on macOS/Windows. Separate cleanup of a demonstrably owned failed operation from recovery of unknown locks; refuse uncertain foreign locks and surface an actionable busy/stale-lock error rather than automatically unlinking. Use portable operation ownership/liveness where provable, preserve/recheck file identity, and do not blindly retry deletion of a replacement file. Include external `git -C`, long hook, platform-unavailable detection, and replacement-race cases in verification. The in-process mutex cannot make foreign-lock deletion safe.
2. **Handler cancellation bypasses cleanup.** `http.rs:1345-1353`; `git.rs:340,375-435`: give mutations a supervised task/operation owner whose lifetime survives request drop and which holds serialization through completion/reaping/cleanup. Await its result from HTTP; dropping a JoinHandle must not abort the owner. Alternatively use a cancellation guard that hands work to an existing supervisor, rather than trying to await filesystem cleanup inside Drop. Verify disconnect/drop while add/commit holds a lock and while cleanup runs. A guard alone is insufficient if it cannot ensure the child has exited before lock removal.
3. **Known-child cleanup skips a recent orphan and silently fails.** `git.rs:368-372,400-408,413-435`: retain enough operation/lock identity to distinguish its own orphan after the child/tree is confirmed dead, then clean that owned lock without requiring 10s of age. If cleanup must be deferred, keep ownership and schedule a supervised retry; report cleanup failure rather than discarding it. Do not simply remove the age check for arbitrary preexisting locks. Reproduce a timeout just after a lock write, not only an artificial 60s-old file.
4. **Only the direct Git process is killed; hook descendants can survive.** `git.rs:333-345,368-372`: supervise an isolated process group / platform process tree (Windows job equivalent), terminate and reap the owned tree before claiming it is safe to clean locks. Current code ignores kill/wait errors and awaits reap without a deadline. Bound/report termination failures and retain safe ownership state. Hooks may continue modifying the index even after the Git parent is gone, and inherited pipes can hold the output-drain future open.
5. **240s commit budget is below the composed server budget, with unbounded queueing.** `git.rs:36-43,45-83,165-172,1019-1062`; `rest.ts:106-109`: define one operation budget including admission/queue, validation, recovery, subprocesses, cleanup and response work, with cleanup reserve; make client commit budget exceed it with margin, or use a durable operation/status API. Resolve/cache repository identity and lock path once per owned operation instead of spending new subprocess budgets on every cleanup. Correct the 210s/“never aborts” comments. Merely changing 240 to 330 cannot bound an unlimited mutex queue or reap.
6. **Generic client config can shrink Git deadlines to 12s.** `rest.ts:132-164,233-242`: make Git-specific budgets authoritative minimums for finite generic timeout settings (preserve explicit 0/no timer), or introduce explicit per-route overrides instead of applying the generic short timeout to mutations. Update config/option precedence tests accordingly; a short options/env/localStorage value currently recreates the incident.
7. **Read paths are unguarded optional index writers.** `git.rs:349-355,709-717,818,1243,1275-1286`: disable optional locks on observational status commands (including TaskAutoCommit status), using per-command `--no-optional-locks` or equivalent. Do not silently disable actual required mutation locks. If a read must write, route it through the same owned writer lifecycle. Verify a status refresh interrupted during an index write.
8. **Per-path mutex permits same-index concurrent writers.** `git.rs:25-26,1015-1021,1299-1307`; `http.rs:1274-1277`: resolve the actual canonical Git-dir/index resource before acquiring the registry mutex, so all project subdirectories and TaskAutoCommit use the same key. Coordinate common-dir operations separately where worktrees share administration; do not assume canonicalizing an input directory discovers repository identity.
9. **Other client route budgets cover one subprocess rather than the whole route.** `rest.ts:110-112,195-199`; `git.rs:709-886,906-963,1238-1256`: align read/stage/unstage/discard/message budgets with composed operation deadlines too. Batch discard where semantics allow or cap its complete operation; model timeout alone excludes diff/status/provider setup. After commit success the UI reload uses these undersized read budgets (`ProjectGit.tsx:203-220,316-317`) and can show a timeout even though commit succeeded.
10. **Worktree mutations bypass the lifecycle and write different/shared resources.** `git.rs:349-355,1466-1509`: when these helpers are used, apply the same supervised operation framework, correct source/target/common-dir serialization, and ownership-safe recovery to worktree mutations; include worktree-specific admin/target index locks rather than only source `.git/index.lock`. Also account for Git's auxiliary temporary index locks in path-limited commits when defining owned lock cleanup; never wildcard-delete foreign lockfiles.
11. **Successful commits can be reported as failures; regression checks miss the dangerous paths.** `git.rs:1048-1067`; `ProjectGit.tsx:310-323,368-374`; `rest.test.ts:687-739`; `git.rs:1796-1876`: distinguish committed-but-metadata-unavailable from commit failure, and reconcile operation state on uncertain/disconnected results before offering a blind retry. Extend tests with actual deadlines/config precedence, fresh orphan timeout, cancellation, external live locks, and same-index aliases. Current client tests mostly assert signal presence/constants, and server tests exercise synthetic aged/fresh locks without killing a writer holding one. They do not validate the composed latency or cancellation guarantees.
